## 2. Track 1 台灣核心實作指引（TW Core IG）
### 2.1 目的
驗證「把非 FHIR 的結構化醫療資料轉換成符合 TW Core Profiles 的 FHIR JSON（FHIRize）」的能力。**不評比** HIS 導入經驗，也不要求 HIS/EHR 全面改造。
- 輸入：Simplified JSON（主要）、結構化欄位表。非結構化資料不列入 2026 年評測。
- 流程（images/twcore-scenarios、twcore-fhirfox）：標準測試資料集（Simplified JSON）→ 參測系統 → TW Core FHIR Resources（Bundle）→ FHIR Validator。驗證工具會**依測試案例編號，逐一和 FHIRfox 產生的「FHIR 標準答案」比對**，並產生測試報告。參測者可以自行把輸入 JSON 改成 CSV 或 DB 等格式再處理。
- 測試資料：由 FHIRfox（https://github.com/cylab-tw/fhirfox ，沙盒 https://cylab-tw.github.io/fhirfox/）產生。模擬 HIS 關聯式資料庫，含 Dataset 與 Code Mapping（SNOMED CT、LOINC、HL7 Code、院內碼）。

### 2.2 角色（Actors）／系統類型
- 網站**沒有**替 Track 1 定義 IHE 式的 Actor/Transaction 表。只列出「涉及系統類型」：FHIR Converter/Middleware、醫療 App（含未連 EHR 的第三方 App）、FHIR Server／平台、資料分析與整合工具。
- 檢核基準：有人機介面的產品，需把測試資料輸入介面並完成測試規範。**轉換器（FHIR Converter）需提交「前測報告」，並通過自動驗證測試腳本**。

### 2.3 驗證三層目的（能力聲明）
1. 單一資源轉換能力
2. 參考資源連結能力（Link to referenced resources）
3. 國際代碼轉換能力（院內碼轉 LOINC/SNOMED CT 等）

能力聲明證明（圖示）共四類：認證模組聲明（管理／臨床／診斷／藥物）、資源能力聲明（單一資源、參考資源）、代碼能力聲明（國際／國內）、情境等級聲明（#1–#5）。
Validator 驗證三面向：TWCDI 內容（欄位、格式、TWCDI 內涵）＋四大模組相容性＋值集／代碼。

### 2.4 測試情境等級（Levels）與測試案例
| Level | 名稱 | 至少涵蓋的資源 | 2026 測試案例 |
|---|---|---|---|
| 1 | 基本就醫紀錄 | Patient、Organization、Encounter、Condition、Practitioner、PractitionerRole | TWCORE-OPD-001（成人門診）、OPD-002（小兒）、OPD-003（同病人多次門診）、ER-001、IPD-001 |
| 2 | 臨床處置與紀錄 | ＋AllergyIntolerance、Condition、Procedure、Observation（vital signs、lab；valueQuantity/unit/effectiveDateTime） | OPD-004、005、006、ER-002、IPD-002 |
| 3 | 用藥與檢查 | ＋DiagnosticReport、Medication、MedicationRequest（圖中另有 MedicationDispense）；藥品代碼為健保碼/ATC，含 dosage、frequency、duration、authoredOn、unit | OPD-007（感冒＋CBC＋感冒藥）、OPD-008（發燒＋CBC＋尿檢＋退燒藥）、OPD-009（慢性病＋HbA1c＋長期用藥）、ER-003（胸痛 ECG＋Troponin＋CXR＋緊急用藥）、IPD-003（住院＋Lab panel＋病理＋多重用藥）、IPS_TWCORE-OPD-010/011、IPS_TWCORE-MIX-001/002/003 |
| 4 | 診斷與檢驗整合 | 影像、報告套餐、基因 | **不在 2026 範圍** |
| 5 | 全人照護（跨院／慢性病／追蹤） | — | **不在 2026 範圍** |

等級為累加設計。欄位選用規則：(1) TWCDI 欄位、(2) TW Core Profile 邏輯模型欄位、(3) 各 Profile 必填欄位。

### 2.5 規格範圍：預計測試的 Profiles（四大模組）
- **管理**：CareTeam、Implantable Device、Location、Organization（Government／Hospital Department／Company）、Patient、Practitioner、PractitionerRole
- **臨床—流程**：Encounter、CarePlan、Goal
- **臨床**：AllergyIntolerance、Condition、Procedure、Specimen
- **觀察與量測**：Observation 六大情境
  - Vital Signs：BP、平均血壓、HR、RR、體溫、SpO2、身高、體重、BMI、頭圍、Pediatric BMI/Weight-for-Height/Head Circumference Percentile
  - Clinical Result／Laboratory Result／ECG／Simple Observation
  - Smoking Status、Sexual Orientation、Occupation
  - Pregnancy Status/Intent
  - Screening Assessment
  - Care Experience／Treatment Intervention Preference
- **診斷**：DiagnosticReport、ImagingStudy
- **藥物**：Medication、MedicationRequest、MedicationDispense、MedicationStatement、Immunization

### 2.7 驗證與通過標準
- 驗證重點：
  - 套用正確的 TW Core Profile（`meta.profile` 必填，validator.dicom.tw 要求）
  - 必填欄位完整
  - 值集與代碼正確（TW ValueSets／LOINC／SNOMED CT）
  - 能通過對應版本的 FHIR Validator
- 工具：
  - 北護「FHIR 一站式驗證工具」https://validator.dicom.tw/app/（說明 https://validator.dicom.tw/app/docs/ ）。驗證結果**不得有 Fatal 與 Error**。
  - IG Package 驗證證明：使用 HL7 `validator_cli.jar`（教學 https://twcore.mohw.gov.tw/ig/twcore/validates.html ）。
- 通過判定：參測者須讓所有測試案例都產出正確結果；Level I 由督察員認證。官方結果的「等級」欄顯示達到的情境 Level（多數為 3）。
- **【網站未提供】** 量化門檻（例如容許的 warning 數、比對的一致率），以及前測報告的格式。

### 2.8 Monitor／Gazelle 證據要求

  - 實體聯測透過 Gazelle Proxy 擷取交易封包。
  - Track 2 寫明轉換器需讓督察員「親自查看 client 系統」。

- 架構（images/platform-arch）：

## 4. 資安／OAuth／SMART／CDS Hooks
- **Track 3 IUA**：
  - 角色：AUTH_CLIENT、AUTH_SERVER、RESOURCE_SERVER。
  - 交易：ITI-71 Get Access Token（R）、ITI-72 Incorporate Access Token（R）、ITI-103 AS Metadata（R）、ITI-102 Introspect（O）、SMART-1 Discovery（O）。
  - Grant 類型：Client Credentials 與 Authorization Code；行動 App 需 PKCE。
  - client 認證：`client_secret` 一律為 `"secret"`，以 HTTP Basic 傳送。
  - scope 值：`twcore`、`twpas`、`ips`、`smart`、`other`。
  - JWT：須以 **RS256** 簽章；必要 claims 為 iss、sub(=client_id)、aud(=resource)、jti、exp、scope、iat；選填 ihe_iua（subject_name、subject_role、purpose_of_use）。
  - ITI-71/72 必須使用 TLS。
  - 無 Token 時，Resource Server 應回 401（未認證）或 403（已認證但無權杖）；並須驗證簽章、exp、scope。
  - Client 與 AS/RS 必須是不同單位；AS 與 RS 可以是同一家。
- **SMART 選項（非強制）**：
  - `.well-known/smart-configuration`、SMART scopes（如 `patient/*`）、EHR Launch／Standalone Launch。
  - 認證支援 private-key JWT（非對稱，Server 必須支援）與 client secret（對稱）。
  - 授權方式包含 App Launch 與 Backend Services。
  - scope 限縮的回傳結果需由督察員現場面對面驗證。
- **全賽道 Level I**：必須用 OAuth2 Client Credentials 向大會 Keycloak 取 Token，才能存取 FHIR／DICOMweb 主機。資料主機前面有 JWT Token Gateway。
- **長照**：LTC-011 取得 OAuth2 Token、LTC-012 以 Token 存取並驗證缺少 Token 時的錯誤回應。
- **CDS Hooks**：**【網站未提供】** 沒有 CDS Hooks 賽道，全站也沒有提到 CDS Hooks。Track 1 只在效益段落提到「為 IPS、SMART App、CDS 等應用奠定基礎」。
